# Contract Acceptance

在接收方项目内检查已经交付的成品，并保存可追溯的本地验收结果。合同属于接收项目，不在本技能复制维护具体格式、目录或版本规则。

## 确定合同和边界

先读接收方约定、README 和当前任务状态，再从 contracts/ 或项目指定位置找到适用合同、Schema、接入配置及检查入口。核对用户指出的成品目录与登记位置；以合同标识、版本及实际文件为准，不凭“最新”目录名选择合同。无法确定匹配合同或成品位置时，先完成独立的只读调查，再问清缺失信息。

生产者决定自己的导出机制和输出位置。合同中的 artifact root 仅代表交付内容的根；除非适用合同明确要求，不假设它叫 dist 或与小说 id 同名。用户负责复制；不调用生产者构建器、不读取或写入其源码目录，也不替用户复制、删除旧包或补全缺失文件。遇到不完整成品，报告具体问题，由用户重新提供完整交付。

在开始写入前按接收项目要求确认流程、任务、精确输出位置和保护范围。接收指令只授权与本次验收相关的本地检查及记录；不自动授权 Git 写操作、发布或远端服务。保护用户已拷入的原始字节；不得原地改正清单、正文或素材来让检查通过。

## 检查交付和本站集成

优先复用项目已有检查器和构建命令。区分合同级接收检查、构建读取保护和生产者业务校验；构建成功不能替代合同完整性检查。若合同指定 Schema，使用项目已有的兼容验证器；没有验证器时可直接核对约束或写局部只读检查，不安装依赖或把一次接收检查强行加入正常构建。明确报告实际覆盖范围及未执行项。

按合同核对根目录、清单身份与必需字段、文件类型和编码、必需文件及包内引用、约定标识与顺序、入口、许可证或 notices 等适用项目。按清单顺序读取，不按文件名重排；不审改内容、不发明生产者编号政策。检查包中未引用文件和遗留文件，因为它们也可能被完整发布；无法从现有证据判断是否应公开的内容应明确列出，不自行删除。拒绝越界路径和目录链接，不跟随链接读取包外数据。

执行接收方正常检查和构建，检查真实输出中的入口、资源和成品原始字节；有适用预览工具时验证新入口的本地可达性。只有涉及界面功能变更时才按项目要求进入界面审阅；普通内容接收不暗含界面重设计。保持成品检查和远端部署结果分开。

## 保存接收结果

遵循项目既有收据及 QA 布局，记录合同身份、交付清单身份、生产者稳定名称和交付版本（提供时）、成品根目录、全部实际文件的 SHA-256、使用的命令、结果和必要的集成证据。复用现有摘要算法并写明算法，避免自创第二套不兼容收据。已有生产者摘要时比较；没有时明确只能证明当前已收到的字节，不能证明传输前一致性。缺失的版本、来源、许可等信息记为 unknown 或 pending，并按合同判断是否阻止接收，不编造信息。

保存本次报告及项目要求的任务控制；历史报告和已接受版本不原地覆盖。本地验收可以标记为 accepted、rejected 或 pending，说明适用范围和剩余阻塞。项目明确允许更新同一当前成品目录时，记录本次新摘要，不额外创建其未要求的历史成品副本。

报告本次接收是否通过、验证到哪些实际字节、未决问题和用户下一步。用户要求接收时完成接收记录，不停留在建议；有合同阻塞时说明条件，不能声称已接收。远端发布始终需要另外的明确授权并遵守用户远端操作边界。
